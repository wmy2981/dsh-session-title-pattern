## 背景

**生成的标题里没有 type**：模板是 `{MMDD}｜{type}｜{topic}`，实际落库的却是
`1025｜全面代码审查`、`1025｜升级工作流 Node 版本并消除警告` —— `{type}` 整段消失。

按设计「模型没按 `类型|主题` 输出时省略类型」，所以问题只可能出在**模型压根没收到指令**。
核实后成立：`@deepseek-ai/dsh-llm-pi-ai` 把 `GenerateOptions.system` 转成
`role: system`（推理模型走 `role: developer`）消息，而 wb2api 代理
（`http://192.168.124.12:7863/v1`，`openai-completions`）**静默丢弃所有
system / developer 消息**。模型只看到一条 user 消息，于是回一句普通标题，第二行不带 `|`。

## 过程

**1. 定位（实机数据 + 直连探测，非推测）。**

- `~/.dsh/sessions` 全量解压、605 条 `session/title` 事件按模型分组统计「是否含 type」：
  - 10-18 当天 wb2api 两个 deepseek-v4.1-flash 路由 **26/26 带 type**；
  - 10-25 同一对路由 **2/58 带 type**，`dsh-opencode-go/deepseek-v4.1-flash` 仍是 63/64。
  - 同一份构建、同一份提示词，只有供应商换了 → 指向供应商行为差异，不是代码回归。
- 直连 `POST /v1/chat/completions` 探测（`global:deepseek-v4.1-flash`）：
  - 300 词 system + `Say OK.` → `usage.prompt_tokens` **58**；不带 system 同样 **58**。
  - `system` 写「密钥词是 PINEAPPLE」再问密钥词 → 答空；同一句放进 user → 答 `PINEAPPLE`。
  - `developer` 角色、数组形式 content、`cn:` 路由、`kimi-k3.1-pro` 全部同样被丢弃；
    多轮 user/assistant 历史正常保留（3 轮记忆测试答对）。
- 结论：这不是本插件的问题，是**该 OpenAI 兼容代理只转发 user / assistant**。
  同一个缺口也会让 dsh 主对话的 system 提示词（`system/message` 事件）到不了模型，
  属于用户侧基础设施问题，另案处理。

**2. 修法：指令与输入拼进同一条 user 消息，不再依赖 `system`。**

- `src/host/llm.ts`：`systemPrompt()` 改名 `instructionPrompt()`（它已经不是 system 了），
  调用处改为 `content: [{ type: 'text', text: `${instructionPrompt(typeLang)}\n\n${input}` }]`，
  并删掉 `GenerateOptions.system`。
- 只留一处：不搞「system + user 各放一份」的双保险 —— 指令重复一遍对听话的供应商是纯冗余，
  而拼进 user 消息对任何供应商都成立。代价只是指令不再享受供应商侧 system 前缀缓存
  （几百字节，可忽略）。
- 提示词内容一个字没动（两行格式、类型语言、两段示例、主线抗漂移全保留）。

**3. 验证。**

- `npm run typecheck` 通过；`npm run build` 重新产出 `lib/`（host + client）。
- 从**打包产物** `lib/index.mjs` 里抽出 `instructionPrompt` 求值，按插件真实入参
  （`buildPromptInput` 的 JSON 形态）直连模型跑两轮，两次都返回两行、第二行带 `|`：

  模板渲染即 `1025｜排查｜…`、`1025｜配置｜…`，`{type}` 段恢复。
